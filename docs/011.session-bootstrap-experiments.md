# 011 Session Bootstrap Experiments

## Goal

Найти минимальный набор передаваемых артефактов сессии, достаточный для запроса к `bonds` API.

## What We Already Know

Из бандла и пробных запросов уже понятно:

- `API_INITIAL` вызывается `POST`;
- в ответе на `API_INITIAL` мы получаем:
  - `status: success`;
  - `data.xref`;
  - `data.base_url = api/p24/pub/`;
  - `data.session_type = public`;
- тот же ответ ставит cookie `pubkey` через `Set-Cookie`;
- `bonds` API расположен на `/api/p24/bonds` и публичном `/api/p24/pub/bonds`;
- без дальнейшего session bridge ответ на `bonds` остаётся `session_was_expired`;
- `redirect`-шаг требует отдельного `sid`, которого нет в текущем `API_INITIAL` payload.

## Experiment Matrix

### E1. `API_INITIAL` as POST

Request:

- `POST /api/p24/init`
- header `X-Requested-With-Alias: testRandomToken`
- body `fingerprint=testRandomToken`

Observed result:

- HTTP `200`
- JSON `status: success`
- `data.xref` present
- `data.base_url = api/p24/pub/`
- `data.session_type = public`
- `Set-Cookie: pubkey=...; HttpOnly`

Interpretation:

- это минимальный успешный bootstrap;
- `pubkey` и `xref` уже доступны;
- этого ещё недостаточно для `bonds`.

### E2. `API_INITIAL` body variants

Requests tested:

- `dyn_string=test`
- `xref=test`
- `fingerprint=testRandomToken`

Observed result:

- все варианты дали успешный ответ;
- `xref` и `pubkey` меняются между прогонами;
- форма body не выглядит критичной для самого `API_INITIAL`.

Interpretation:

- важен сам `POST` + alias header;
- тело запроса не показывает явной зависимости от `dyn_string` или `xref` в этом контуре.

### E3. `bonds:list` with `pubkey + xref`

Requests tested:

- `GET /api/p24/bonds?action=list`
- `POST /api/p24/bonds`
- `GET /api/p24/pub/bonds?action=list`
- `POST /api/p24/pub/bonds`

Common inputs:

- cookie jar from `API_INITIAL`
- `xref` from `API_INITIAL`
- `X-Requested-With-Alias: testRandomToken`
- in some cases `X-Requested-With: XMLHttpRequest`

Observed result:

- HTTP `400`
- `error_code: 95`
- `message: session_was_expired`

Interpretation:

- `pubkey + xref` is not enough;
- есть ещё один обязательный session artifact.

### E4. `redirect` bridge with `xref`

Request:

- `POST /api/p24/redirect`
- body `xref=<value from API_INITIAL>`

Observed result:

- HTTP `400`
- `error_code: 51`
- `message: sid is undefined`

Interpretation:

- `redirect` явно ждёт ещё один параметр `sid`;
- `xref` alone не хватает.

### E5. `redirect` bridge with candidate `sid`

Requests tested:

- `sid=<xref>`
- `sid=test`

Observed result:

- та же ошибка: `sid is undefined`

Interpretation:

- либо `sid` передаётся не тем способом;
- либо это не тот `sid`, который мы угадываем;
- либо он вообще должен появляться из другого endpoint/flow.

### E6. `refresh?dyn_string=...`

Requests tested:

- `/p24/refresh?dyn_string=test`
- `/p24/refresh?dyn_string=<xref>`

Observed result:

- HTTP `200`
- обычная HTML-страница `Privat24`
- никаких видимых cookies или сессионных артефактов не появилось

Interpretation:

- сам `refresh` без правильного `dyn_string` не даёт session bridge;
- текущая попытка не продвинула нас к `bonds`.

### E7. `init?dyn_string=...` with fresh `pubkey` jar

Request:

- `POST /api/p24/init?dyn_string=testRandomToken`
- header `X-Requested-With-Alias: testRandomToken`
- cookie jar from fresh `API_INITIAL`

Observed result:

- HTTP `500`
- empty body

Interpretation:

- `createSession` действительно идёт через query param `dyn_string`;
- случайное значение не проходит дальше init-bridge;
- без валидного `dyn_string` этот путь не раскрывает новый session artifact.

### E8. `redirect` with fresh `pubkey` jar

Request:

- `POST /api/p24/redirect`
- body `xref=<value from fresh API_INITIAL>`
- header `X-Requested-With-Alias: testRandomToken`
- cookie jar from fresh `API_INITIAL`

Observed result:

- HTTP `400`
- `error_code: 51`
- `message: sid is undefined`
- `Set-Cookie: skey=; expires=Thu, 01-Jan-1970 00:00:01 GMT; max-age=0; version=1; path=/; HttpOnly`

Interpretation:

- `redirect` does not just fail silently, it also manipulates `skey`;
- `skey` looks like part of the bridge state, even though we still do not have a valid `sid`.

## Historical Minimum Current Session Artifact Set

Пока минимальный набор, который мы реально умеем получить:

- `pubkey` cookie;
- `xref` из `API_INITIAL`;
- `base_url = api/p24/pub/`;
- `session_type = public`.
- иногда `skey` присутствует как cookie state marker, но пока только в очищенном виде после неудачного `redirect`.

Но этот набор пока не достаточен для `bonds:list`.

## Current Hypothesis

С высокой вероятностью нам не хватает одного из следующих артефактов:

- `sid` из отдельного public-session flow;
- `skey` cookie, которую сервер, судя по ответам, ожидает как часть bridge;
- или промежуточного запроса, который не виден в текущем `API_INITIAL` ответе.

## Next Experiments

1. Проверить, передаётся ли `sid` как query param, а не как form field.
2. Проверить, существует ли скрытый endpoint или browser callback, который возвращает валидный `dyn_string` для `createSession`.
3. Проверить, меняется ли ответ `bonds:list` при наличии дополнительного cookie, если он появится.
4. Снять сетевой след из реального browser flow, чтобы увидеть, какой именно request создаёт `sid` и `dyn_string`.
5. Если `sid` или `dyn_string` найдём, повторить `redirect` -> `createSession` -> `refresh` -> `bonds:list` как полный минимальный цикл.

## Bridge Update

Новый успешный мини-кейс показал, что bridge живёт не только вокруг `API_INITIAL`, но и вокруг `/http`:

- точный header `X-Request-origin: https://next.privat24.ua` открывает success-path на `https://www.privat24.ua/http`;
- `Origin` без `X-Request-origin` не даёт нужного bridge-ответа;
- `GET /http?phone=380501234567` с этим header создаёт cookie `defaultPageToken_*`;
- следующий `GET /http` с тем же cookie возвращает `show_ivr_form` и отдаёт `phone`, `ivrPhone`, `alternate_cmd` и `alternate_cmd_timer`;
- это состояние одноразовое: один follow-up `GET` съедает очередь, после чего ответ снова деградирует до пустого `success`;
- `phone=test` даёт `unsupported_registration_for_foreign_client`, что подтверждает наличие server-side validation;
- `login`, `card_id`, `sms_incoming_password` и `ivr_3digits` принимаются как запросы, но в наблюдаемом flow не создают reusable queued state.

## Updated Minimum Current Session Artifact Set

Пока минимальный набор, который мы реально умеем получить:

- `pubkey` cookie;
- `xref` из `API_INITIAL`;
- `base_url = api/p24/pub/`;
- `session_type = public`;
- `defaultPageToken_*` cookie из успешного `/http` bridge;
- one-time queued state, который впервые проявляется на следующем `GET /http` после `phone=...`.

Это и есть текущий минимальный bridge-контур, который стоит использовать в handoff и следующих экспериментах.
